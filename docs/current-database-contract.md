## Accounts, bookings, and active services

`profiles` uses `id uuid` as its PK/FK to `auth.users`, not `user_id`. Other columns are nullable `full_name text`, `phone text`, `avatar_url text`; required `role text` default patient and `created_at timestamptz` default now. Names/phones have no catalog length/check constraint. Own SELECT/INSERT/UPDATE policies exist, and authenticated has table privileges for those operations. Read/write the captured user's `id` explicitly. The role check permits `patient, doctor, nurse, hospital, clinic, laboratory, pharmacy, ambulance, instructor, admin`.

`handle_new_user()` creates the profile from signup metadata, but attached `protect_profile_role_trigger` forces **every INSERT to patient**. It suppresses a changed role on UPDATE unless the current authenticated user's stored profile role is admin. Metadata, an occupation choice, or a public form cannot grant provider/admin authority. `private.is_current_user_admin() -> boolean` checks the current auth UID's stored admin role; it accepts no other user ID, is SECURITY DEFINER with empty search path, and is executable only by authenticated. It is a private policy helper, not a verified public client RPC.

`services`: required `id uuid` (generated PK), `name text`, `slug text` (UNIQUE), `is_active boolean` default true, `sort_order integer` default 100, `created_at`; optional description/image URL. SELECT for anon/authenticated is restricted to active services; no service INSERT/UPDATE/DELETE policy was found. Service names are **not unique** in the catalog.

`bookings`: generated UUID PK `id`; required `user_id uuid`, `service text`, `patient_name text`, `phone text`, `booking_date date`, `status text` default `قيد المراجعة`, `created_at`; optional `notes`, `provider_profile_id uuid`, `service_request_id uuid`. Authenticated table INSERT/SELECT exists. INSERT RLS requires the current UID and status `pending` or `قيد المراجعة`; SELECT permits only the owner. No UPDATE/DELETE or admin SELECT policy exists. There is no status CHECK, idempotency-key column, submission RPC, or `updated_at` column.

The BEFORE INSERT `link_booking_service_request()` trigger requires authentication/ownership, selects an active service by its **name**, rejects dates before today in Africa/Tripoli, and creates the linked `service_requests` row atomically. Optional provider association supports only service slugs `doctors`, `home-nursing`, and `hospitals`; it requires the matching verified provider, plus available home visits for nurses. It does not check city. Dates represent days, not a confirmed appointment time.

Client-chosen UUIDs are allowed by the booking PK/privileges. Lost-response recovery can SELECT that same ID under the captured owner; no duplicate recovery RPC exists. Preserve the original UUID and payload for an unresolved attempt. On retry, resolve a possibly saved row before rejecting an elapsed date: the BEFORE INSERT date trigger can raise before a duplicate PK check. A failed booking transaction rolls back its linked request insertion.

`service_requests`: generated UUID PK, required `requester_id uuid`, status default pending, timestamps; optional service/assigned-provider UUIDs, requested timestamp, address, coordinates, notes. Status CHECK: `pending, accepted, on_the_way, in_progress, completed, cancelled`. Requester/assigned provider/admin can SELECT and UPDATE; INSERT requires current requester. The existing UPDATE policy checks participation, **not** state transitions or which columns may change. No request trigger or transactional status RPC was found. Booking rows and linked request status are not synchronized by an UPDATE trigger.

Provider-specific tables additionally let owners SELECT their own unverified records. Public screens should explicitly filter verified records rather than treating owner-visible drafts as approved. Provider INSERT requires the matching stored profile role and owner ID; UPDATE preserves ownership through RLS. **Those five provider tables have no verification-protection trigger or admin-specific write policy.** Owners have table-wide INSERT/UPDATE privileges, so the `verified` boolean is not a server-protected administrator approval field.

Organizations allow authenticated own INSERT/SELECT/UPDATE and admin ALL. Kind CHECK: `hospital, clinic, ambulance, training_center, medical_center, other`. Verification CHECK: `pending, verified, rejected`; defaults to pending. `protect_organization_verification()` forces pending/null review data on non-admin INSERT and preserves review data on non-admin UPDATE. Organization timestamps have no automatic touch trigger. This path is stronger than the separate hospital/lab/pharmacy verification booleans.

Jobs allow owner SELECT/UPDATE/DELETE, provider INSERT for stored roles doctor/nurse/hospital/clinic/laboratory/pharmacy/ambulance/instructor/admin. Status CHECK/default: active or closed, default active; no moderation guard or admin policy. Applications use required `job_id, applicant_id`, optional note/CV, unique `(job_id, applicant_id)`; statuses submitted/reviewing/shortlisted/accepted/rejected/withdrawn. Applicants insert submitted and may update only to withdrawn; publishers read/update applicants to their jobs. There are no additional field-specific update guards.

Courses allow owner SELECT/UPDATE/DELETE; INSERT uses the same provider roles except ambulance; admin SELECT/UPDATE. Course status active/closed defaults active. `review_status` draft/pending/approved/rejected defaults draft, but public SELECT checks **only active**, and no guard protects review fields: draft or rejected courses may still be public. Learning outcomes default `[]`, is-free false, nonnegative duration; other price/seats/date bounds are not checked in the inspected constraints. `doctors_with_rating` and `upcoming_appointments` views both use `security_invoker=true`.

## Provider approval RPC and backend gaps

`approve_provider_application(p_application_id uuid, p_approve boolean) -> void` is authenticated-only SECURITY INVOKER. It checks current stored admin role, locks the application, updates approved/rejected + reviewer/time, and on approval updates the user's profile role. It has no pending-only condition, stale timestamp, or affected-row verification.

Applications require `user_id, requested_role`; optional license/organization/city/phone/notes; status defaults pending. Requested roles are doctor/nurse/hospital/clinic/laboratory/pharmacy/ambulance/instructor/**government**. A verified **RESTRICTIVE** INSERT policy requires pending status and null reviewer/time, in addition to permissive own INSERT. Applicant/admin can read; only admin can update.

The metadata proves these backend changes are needed before presenting the associated workflows as complete:

1. **Provider approval:** profiles has only own SELECT, despite admin UPDATE. The invoker RPC's UPDATE of another profile is filtered by that missing admin SELECT permission; it can mark an application approved while matching no profile row. `government` also fails the profiles role CHECK. Repair the transaction/authorization contract and verify affected rows before implementing promotion UI; do not silently show successful role approval.
2. **Provider verification:** protect verification fields and add an intentional reviewer path for doctor/nurse/hospital/lab/pharmacy records; current owner-writable booleans cannot represent independent verification.
3. **Admin bookings/status:** add authorized administration and an atomic booking/request state-transition contract if the admin panel must review all bookings. Current booking RLS provides neither admin reading nor updates; current participant request updates do not constrain transitions. Existing organization and course admin policies alone do not cover this gap.
4. **Course publication/enrollment:** publication does not enforce approved review. Enrollment INSERT's paid branch requires the course status to be both active and pending; pending is also forbidden by the course CHECK, so that branch is unreachable. Free enrollment permits `payment_status='free'`, but does not constrain enrollment status beyond its general CHECK. Fix that contract before claiming paid enrollment or verified publication. Enrollments already have user/course-publisher read, admin update, unique course/user, status pending/active/completed/cancelled/refunded and payment unpaid/pending/paid/failed/refunded/free.
5. **Scope:** jobs, applications, course lessons/enrollments, messages, community posts, promotions, and wallets already have backend tables. Their missing static UI is not evidence that duplicate tables or old Lovable RPCs should be created. No product/order/shop inventory table or payment processing RPC appeared in the inspected public/private inventory; a real shop needs its own verified transaction/backend contract. Messaging/community/payment operations outside the tables above still need focused source/policy inspection before implementation.
